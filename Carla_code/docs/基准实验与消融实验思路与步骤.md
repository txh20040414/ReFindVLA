# ReFindVLA 基准实验与消融实验思路与步骤

> 本文档用于 ReFindVLA camera-ready 返修实验。它统一实验目标、比较对象、代码隔离原则、episode 数量、运行步骤、日志要求、统计方法和论文写法。
>
> 重要原则：没有原始日志的数字不得填入新结果表；历史文档中的数字必须标明批次、分母和配置版本。

## 1. 实验要回答的核心问题

本轮实验不是单纯证明 CARLA-Air、Memory、Belief Map、候选验证和控制器组成的混合系统可以运行，而是要回答审稿人反复提出的核心问题：

> 在 Target Memory、Search Belief Map、Candidate Verification、语义航点规划器和 Safety Controller 均保持不变时，Qwen2.5-VL 高层 VLA 决策是否带来可测量的增益？

因此，实验必须把 ReFindVLA 拆成两个只改变高层决策来源的版本：

    同一个 DecisionContext
            ├── Remote Qwen VLA policy
            └── Rule-based high-level policy
                        ↓
            同一个语义航点规划器
                        ↓
            同一个低层安全控制器
                        ↓
            同一个 CARLA-Air / AirSim 评价过程

不能使用“完整 ReFindVLA vs. 旧版 Rule Search”作为 VLA 的严格消融，因为旧版 Rule Search 可能同时改变搜索策略、历史线索、信念图和候选处理方式。那种比较只能说明整体系统差异，不能单独估计 VLA 的贡献。

## 2. 系统拓扑与方法定位

    Windows 本地控制机
      CARLA-Air v0.1.7
      CARLA Python API 0.9.16
      AirSim Python API 1.8.1
      Code/main_interactive_track
              │ HTTP POST /predict
              ▼
    Linux GPU 服务器
      Qwen2.5-VL-7B-Instruct
      ReFindVLA LoRA adapter
      Code/model_server.py:8000

Qwen 只输出高层结构化决策，例如：

    {
      "phase": "search",
      "view": "top",
      "target_found": false,
      "confidence": 0.42,
      "hold_seconds": 5,
      "reason": "沿目标最后运动方向搜索东侧道路"
    }

Qwen 不直接输出无人机底层速度。vx/vy/vz/yaw_rate 由本地 decision.py、controller.py 和 AirSim 接口生成。因此论文应把 ReFindVLA 定义为：

    a high-level vision-language planning layer for UAV dynamic target reacquisition

而不是端到端底层飞控模型。

## 3. 实验总矩阵

### 3.1 最小正式实验

每种策略运行 22 个 episode，共 88 次策略运行：

| 编号 | 策略 | 每种 episode 数 | 总作用 | 当前状态 |
|---|---|---:|---|---|
| E0 | Smoke test | 1 | 检查环境、HTTP、模型和日志 | 已有入口，不计入论文结果 |
| E1 | Full ReFindVLA | 22 | 完整远程 VLA 系统 | 当前代码已有入口 |
| E2 | Strict No-VLA | 22 | 隔离远程 VLA 高层决策贡献 | 当前代码已有入口 |
| E3 | A* Waypoint | 22 | 传统几何搜索基线 | 当前仓库没有可核验的独立实现 |
| E4 | Exponential Spiral | 22 | 传统空间搜索基线 | 当前仓库没有可核验的独立实现 |

总数：

    4 种正式策略 × 22 episodes = 88 policy-episode runs

每一种方法的统计分母仍然是 N=22，不能把四种方法合并成 N=88 来计算某一种方法的 RSR。

### 3.2 可选候选验证消融

如果完成候选验证开关和日志检查，可以再增加：

| 编号 | 策略 | episode 数 | 目的 |
|---|---|---:|---|
| A2 | w/o Candidate Verification | 22 | 评估候选确认模块对误找回和成功率的影响 |

此时总运行数为：

    88 + 22 = 110 policy-episode runs

这已经是本轮返修的合理上限。

### 3.3 明确不作为本轮必做的实验

以下实验不作为当前 camera-ready 的必做项目：

- w/o Target Memory；
- w/o Search Belief Map；
- w/o Safety Controller；
- 多个 LoRA rank 的重新训练；
- 0.60/0.70/0.80 阈值敏感性扫描；
- 多个 Qwen 基座模型；
- 最新学习型空中 VLA 数值复现；
- 真机无人机实验；
- 全部组件的排列组合消融。

## 4. 22 个 episode 的场景协议

### 4.1 匹配 manifest 原则

E1、E2、E3、E4 必须使用同一个 episode manifest。每个 episode 至少记录：

    episode_id
    random_seed（如果当前仿真器/脚本支持）
    map_name
    target_vehicle_type
    target_vehicle_color
    target_spawn_point
    target_initial_state
    background_traffic_configuration
    weather
    loss_or_occlusion_trigger
    max_steps
    timeout

同一 episode_id 在不同策略下代表同一个实验场景。不能为每一种策略重新随机生成 22 个场景后，再把结果称为严格成对消融。

如果 CARLA-Air 无法保证场景完全确定性复位，应保存完整 manifest，并在论文中使用 matched scenario protocol，不要声称完全确定性复现。

### 4.2 场景覆盖

如果使用已有 22 集批次，必须从实际 manifest 统计场景分布，不得根据计划文档反推数量。

如果重新设计 22 集，不要求各类完全等量，但必须覆盖以下场景并在 manifest 中记录实际数量：

| 场景 | 覆盖要求 |
|---|---:|
| 建筑/树木遮挡 | 必须覆盖 |
| 路口或道路分支歧义 | 必须覆盖 |
| 远距离消失或视场受限 | 必须覆盖 |
| 相似车辆干扰 | 必须覆盖 |
| 停车场或目标由动态变静态 | 尽量覆盖 |

22 集是每种方法的总数，不应为了凑数量删除某一场景类别。最终论文必须报告实际数量和分布。

### 4.3 固定环境配置

首选统一配置：

- CARLA-Air：v0.1.7；
- CARLA API：0.9.16；
- AirSim：1.8.1；
- 地图：Town10HD；
- 控制步长：0.5 s；
- 高层决策间隔：5.0 s；
- 最大步数：以当前代码的 run_config.json 为准；
- 当前默认背景交通：8 辆；
- 相机默认采用 RECOVER_CAMERA_CONTROL=0 的静态 settings 配置；
- 坐标偏移必须记录来源，不得当作跨地图常数。

历史资料曾使用过 10 辆背景车和 0.55/0.45/0.55 阈值组合；当前代码默认值为：

    confirm_threshold = 0.72
    inspect_threshold = 0.52
    memory_update_threshold = 0.70
    candidate_margin = 0.06
    background_traffic = 8

历史批次和当前代码默认值不可以混用。每次运行必须把实际环境变量写入 run_config.json。

## 5. VLA 贡献的代码隔离原则

### 5.1 统一 DecisionContext

完整系统和 no-VLA 对照必须接收同一个结构化上下文：

    DecisionContext = {
        "observation": current_observation,
        "target_memory": target_memory_snapshot,
        "belief_map": belief_map_snapshot,
        "candidates": candidate_verification_results,
        "environment": road_and_building_context,
        "safety": safety_state,
    }

E2 不能读取 CARLA Ground Truth，也不能读取 Qwen 的输出。

### 5.2 两个高层策略

    RemoteVLAPolicy(context) -> structured high-level decision
    RulePolicy(context)      -> structured high-level decision

两者都只能输出：

- phase；
- view；
- target_found；
- confidence；
- hold_seconds；
- reason。

两者都不能直接输出或绕过本地低层控制量。

### 5.3 完整系统 E1

    export RECOVER_USE_REMOTE_VLA=1
    export RECOVER_REMOTE_REQUIRED=1
    python3 -m main_interactive_track.main

执行过程：

1. 读取当前图像和 UAV 状态；
2. 更新 Target Memory；
3. 更新 Search Belief Map；
4. 运行 Candidate Verification；
5. 组装 DecisionContext；
6. 通过 HTTP 请求 Qwen；
7. 解析高层 JSON；
8. 用共享航点规划器生成语义航点；
9. 用共享安全控制器生成 AirSim 控制量；
10. 保存原始决策和控制日志。

### 5.4 严格 no-VLA E2

    export RECOVER_USE_REMOTE_VLA=0
    export RECOVER_REMOTE_REQUIRED=0
    python3 -m main_interactive_track.main

执行过程与 E1 完全相同，唯一差别是：

    E1: DecisionContext -> Remote Qwen VLA
    E2: DecisionContext -> local RulePolicy

E2 仍然保留 Target Memory、Search Belief Map、Candidate Verification、语义航点规划器、Safety Controller 和同一终止条件。因此，E2 才是 VLA 决策层的消融，而不是旧版持续跟踪实验。

## 6. 建议的策略接口设计

如果需要进一步强化代码的可读性，可以使用统一策略接口：

    class HighLevelPolicy:
        def decide(self, context):
            raise NotImplementedError

    class RemoteVLAPolicy(HighLevelPolicy):
        def decide(self, context):
            # HTTP 请求 Qwen，返回结构化高层 JSON
            ...

    class RulePolicy(HighLevelPolicy):
        def decide(self, context):
            # 只使用 context，不读取 Ground Truth 和 Qwen 输出
            ...

recover_vla.py 中只进行一次策略选择：

    context = build_decision_context()

    if config.use_remote_vla:
        decision = remote_vla_policy.decide(context)
    else:
        decision = rule_policy.decide(context)

    waypoint = shared_waypoint_planner.to_waypoint(decision, context)
    control = shared_safety_controller.to_control(waypoint, context)

不要在多个函数中分散判断 RECOVER_USE_REMOTE_VLA，否则可能导致 E1/E2 实际使用了不同的候选处理或控制分支。

    ├── episode_summary.json
    ├── environment_meta.json

      "policy_source": "rule_policy",

## 8. 可选的同状态离线 replay

在线 E1/E2 运行后，两个系统的轨迹会逐渐不同。为了进一步分析 VLA 的决策贡献，可以额外保存每个决策时刻的上下文：

    decision_context.jsonl

每一行包括：

    {
      "episode_id": "episode_001",
      "frame_index": 120,
      "image": "frames/frame_000120.png",
      "target_memory": {},
      "belief_map": {},
      "candidates": [],
      "environment": {},
      "safety": {}
    }

然后用同一个上下文分别调用 RemoteVLAPolicy 和 RulePolicy，比较：

- phase；
- search_region；
- target_found；
- confidence；
- JSON parse rate；
- 候选接受/拒绝；
- 搜索区域是否覆盖真实目标位置；
- 错误确认率；
- 高层决策延迟。

Ground Truth 只能用于离线评价，不能作为策略输入。离线 replay 不需要重新运行 CARLA；如果没有完整上下文标签，就不要捏造 phase accuracy 或 search-region accuracy。

## 9. 主实验指标

### 9.1 Episode-level 指标

    RSR = successful_reacquisition_episodes / total_episodes

本轮每种方法的分母固定为 22。例如：

    20/22 = 90.9%
    19/22 = 86.4%
    21/22 = 95.5%

RSR 必须同时报告成功数和总数，不能只写百分比。所有方法都必须报告以下共同指标：

| 指标 | 定义 | 统计方式 |
|---|---|---|
| RSR | 成功找回的 episode 数 / 22 | episode-level，报告 x/22 |
| TTR | 从目标丢失触发到正确确认的时间 | 报告 mean、median、范围和有效样本数 |
| Path Length | 目标丢失后到找回或终止期间的 UAV 飞行距离 | 报告 mean、median、范围 |
| Episode Duration | 完整 episode 墙钟时间 | 报告 mean、median、范围 |
| Collision Rate | 发生碰撞的 episode 数 / 22 | 报告分子和分母 |

Path Length 必须在论文中选定一种口径。如果日志计算的是目标丢失后的搜索距离，就称为 Search Path Length；如果日志包含起飞、搜索、确认和跟踪的全部距离，就称为 Episode Path Length。不能把两种口径混用为同一个 SPL。

### 9.2 Full 和 No-VLA 的候选与安全指标

Full ReFindVLA 和 No-VLA 都保留 Candidate Verification，因此还应报告：

| 指标 | 定义 |
|---|---|
| False Reacquisition Episode Rate | 出现错误确认的 episode 数 / 22 |
| False Confirmation Event Rate | 错误确认事件数 / 全部候选确认事件数；必须明确事件分母 |
| Candidate Evaluation Count | 候选车辆被验证的总次数及每 episode 平均值 |
| Candidate Confirmation Accuracy | 候选身份判断正确数 / 有身份标签的候选总数 |
| Memory Update Count | Target Memory 更新总次数及每 episode 平均值 |
| Candidate Precision/Recall | 只有在候选级 Ground Truth 标签完整时才报告 |

False Reacquisition Event Rate 不能直接把错误事件数除以 22 后称为 episode rate。若候选级标签不完整，只报告有定义依据的 episode-level 指标。

### 9.3 A* 和 Spiral 的适用指标

A* 和 Spiral 当前没有 Candidate Verification 或远程 VLA，因此以下指标应写 N/A，而不是写 0：

| 指标 | A*/Spiral 处理 |
|---|---|
| RSR | 报告 |
| Path Length | 报告 |
| Episode Duration | 报告 |
| Collision Rate | 报告 |
| Candidate Confirmation Accuracy | N/A |
| False Reacquisition | 没有统一候选确认定义时写 N/A |
| Memory Update Count | N/A |
| VLA Latency | N/A |

0 表示测量结果为零，N/A 表示该方法没有对应模块或没有可比定义，二者不能混用。

### 9.4 Decision-level 指标

- JSON Parse Rate；
- Phase Accuracy；
- Search Region Accuracy；
- Candidate Confirmation Accuracy；
- BBox IoU（如果有对应标注）；
- 平均请求延迟；
- P95 请求延迟；
- HTTP timeout/error 次数；
- fallback 次数；
- memory update 次数。

E1 还必须记录 Qwen 请求数、平均延迟和 P95 延迟。E2 不访问远程 Qwen，延迟应写 N/A，而不是写 0。不能用决策请求数作为 RSR 分母，一个 episode 内的多个 Qwen 请求仍然只对应一个 episode。

### 9.5 VLA 增量指标

    ΔRSR  = RSR(Full) - RSR(No-VLA)
    ΔTTR  = TTR(No-VLA) - TTR(Full)
    ΔPath = Path(No-VLA) - Path(Full)
    ΔCollision = Collision(No-VLA) - Collision(Full)

还应记录 22 个配对 episode 中的：

- Full 成功、No-VLA 失败的 episode 数；
- No-VLA 成功、Full 失败的 episode 数；
- 两者都成功的 episode 数；
- 两者都失败的 episode 数。

建议表述：

> The paired comparison estimates the incremental contribution of the high-level VLA decision layer under a fixed downstream recovery pipeline.

不要写成 “VLA alone caused all improvements”。在线实验是固定下游系统下的 matched controlled comparison，不应过度宣称为绝对因果证明。

## 10. 候选验证消融 A2

如果完成该实验，A2 只关闭候选确认门控，其他部分不变：

    Full ReFindVLA：22
    w/o Candidate Verification：22

比较：

- RSR；
- False Reacquisition；
- Candidate Confirmation Accuracy；
- TTR；
- Path Length；
- Collision Rate。

不能把历史资料中的 45 集 No Verification 直接当作与新的 22 集 Full 成对消融。若使用历史 45 集，只能写成 independent diagnostic batch with a different denominator and configuration。

## 11. A* 和 Spiral 基线

A* 和 Spiral 可以作为几何搜索参考，但必须明确其限制：

- 使用相同地图和相同终止条件；
- 最好使用相同 episode manifest；
- 使用相同碰撞判定；
- 保存脚本路径和 commit；
- 保存逐 episode 原始轨迹；
- 不把 CARLA Ground Truth 投影检测称为真实视觉检测；
- 不把几何基线宣称为最新学习型无人机 baseline。

当前仓库没有可直接核验的独立 A* 或 Spiral 入口。如果队员没有提供真实脚本，论文中应保留历史记录并明确为 historical geometric references，不能声称本仓库已完成复现。

## 13. 时间估算

历史资料中完整 RecoverVLA episode 平均约 169.7 秒，但该数字包含初始化、控制和模型推理，仅用于运行时间估算，不是新实验结果。

| 工作 | 纯运行估计 | 实际建议预留 |
|---|---:|---:|
| E0 smoke test | 10–20 分钟 | 半天 |
| E1，22 集 | 约 63 分钟 | 2–4 小时 |
| E2，22 集 | 通常短于 E1 | 1.5–3 小时 |
| E1+E2 | 44 个正式 episode | 半天到一天 |
| A2，22 集 | 与 E1 接近 | 2–4 小时 |
| 四种方法共 88 集 | 取决于基线实现 | 1–2 天 |

人工重置 CARLA、网络异常、目标车生成失败、服务重启和失败 episode 重跑都会增加实际时间。

## 14. 训练实验不需要重新做的部分

本轮在线消融不要求重新训练 Qwen：

- E1 和 E2 使用同一个 Qwen LoRA adapter；
- E2 只是不调用 Qwen；
- 不需要重新训练一个 no-VLA 模型；
- 不需要做 LoRA rank sweep；
- 不需要重新生成大规模训练数据。

当前本地可核对的 RecoverVLA adapter 配置为：

    r = 8
    alpha = 16
    dropout = 0.05
    target_modules = q_proj/k_proj/v_proj/o_proj
    task_type = CAUSAL_LM

训练样本和验证样本的具体原始 JSONL 当前没有随工作区完整保留，因此不要因为在线实验重新运行就把训练数据规模写成新的数字。

## 15. 统计和论文写法

### 15.1 样本量表述

推荐英文表述：

> We evaluate four policies on a common matched manifest containing 22 CARLA-Air episodes. Each policy is executed once on every episode, resulting in 22 episodes per policy and 88 policy-episode runs in total. The total of 88 refers to accumulated executions across policies; all policy-level statistics use N=22 as their denominator.

### 15.2 VLA 消融表述

推荐英文表述：

> To isolate the contribution of the VLA decision layer, the Full and No-VLA variants share the same target memory, belief map, candidate verifier, semantic waypoint planner, safety controller, episode manifest, and termination criteria. The only changed component is the high-level decision source: the Full variant queries Qwen2.5-VL, whereas the No-VLA variant uses the local rule policy.

### 15.3 结果表

    Method                    N     RSR       TTR       Path      Duration   Collision
    A* Waypoint               22    x/22      ...       ...       ...        ...
    Exponential Spiral        22    x/22      ...       ...       ...        ...
    ReFindVLA                 22    x/22      ...       ...       ...        ...
    No-VLA                    22    x/22      ...       ...       ...        ...

不要把旧的 20/22=90.9%、23/25=92.0%、23/23=91.3% 混在同一个新表中。每一行必须标明对应批次和分母。

### 15.4 统计限制

每种方法 N=22 可以支撑仿真可行性和机制对比，但不能支撑过强的普适性结论。建议：

- 同时报告分子和分母；
- 报告 mean、median 和范围；
- 必要时报告 Wilson 或 exact binomial interval；
- 对 E1/E2 使用 episode-level paired comparison；
- 不把 88 次累计运行当作单一方法的 N=88；
- 不声称 statistically conclusive；
- 使用 under the matched simulator protocol、supports feasibility 等谨慎措辞。

## 16. 当前资料中不能混用的历史数字

当前资料曾出现多个不同批次：

- 22 集公平对比：RecoverVLA 20/22=90.9%；
- 25 集独立完整批次：23/25=92.0%；
- 23 集旧诊断批次：23/23=91.3%；
- A* 完整记录中还出现 7/24=29.2%；
- 历史阈值曾使用 0.55/0.45/0.55；
- 当前代码默认阈值为 0.72/0.52/0.70。

这些数字不能直接拼成一个“50 次运行”结果。当前新实验必须建立新的批次目录、manifest、配置和 summary。

## 17. 实验完成判定

一组实验只有同时满足以下条件，才可以写入 camera-ready 结果表：

- [ ] 每个策略均有 22 个 episode 或明确记录排除原因；
- [ ] E1/E2 使用同一 manifest；
- [ ] E1/E2 只改变高层决策来源；
- [ ] run_config.json 保存完整环境变量；
- [ ] 保存 Git commit；
- [ ] 保存 Qwen base model 和 LoRA adapter 路径；
- [ ] 保存 GPU、CUDA、Torch 和 Python 版本；
- [ ] 每个 episode 有 decision.jsonl；
- [ ] 汇总脚本能够重新生成 summary.csv；
- [ ] RSR 分母是 episode 数；
- [ ] 失败 episode 有原因；
- [ ] smoke test 没有混入正式结果；
- [ ] 历史批次没有与新批次混合；
- [ ] 所有论文数字能够回溯到原始日志。

## 18. 最终建议

本轮优先级如下：

1. 先完成 E0，确保 HTTP、CARLA-Air、Qwen 和日志全部正常；
2. 用同一 manifest 完成 E1 的 22 集；
3. 不改变其他模块，完成 E2 的 22 集；
4. 如果 A*/Spiral 脚本真实存在且可接入，再运行各 22 集；
5. 如果时间允许，再加入 A2 w/o Candidate Verification 的 22 集；
6. 不重新运行全部组件组合，不做多基座模型和真机实验；
7. 结果表只使用能由原始日志重新生成的数字。

最终最小方案：

    Full ReFindVLA：22
    No-VLA：22
    A*：22（若脚本可核验）
    Spiral：22（若脚本可核验）
    总计：88 次策略运行

加强方案：

    88 + w/o Candidate Verification 22
    = 110 次策略运行

这套方案的重点不是堆积运行次数，而是在固定下游系统的条件下，直接量化 Qwen VLA 高层决策相对于本地规则策略的增量价值。
